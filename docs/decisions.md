# Decisions

Each entry: what was decided, why, and what it costs. The trade-off column is the
part that matters — a decision without a stated cost is not a decision.

---

## 1. Only completed assessments sync

Drafts stay local. The first operation is created at completion time.

**Why.** It removes the race between debounced auto-save and an in-flight upload
entirely. There is never a question of what happens when the user edits something
that is currently uploading.

**Cost.** Work in progress is not backed up to the server. If the device is lost
mid-inspection, the draft is gone. Acceptable for a single-inspector,
single-device workflow.

---

## 2. The outbox is the source of truth for sync

An Operation table, not a status enum on the entity.

**Why.** Retry, backoff, `nextAttemptAt`, idempotency keys and ordering are
per-operation state. A single enum cannot hold them. And an entity can produce
more than one operation.

**Cost.** A third table, mapping code, and a queue to reason about. Worth it —
this is the project.

---

## 3. Sync status is derived, never stored

Computed from the operations belonging to the assessment and its evidences.

**Why.** Two sources of truth for the same fact will eventually disagree, and the
crash window between updating one and the other is exactly the scenario this app
is about.

**Cost.** A query per assessment on display. Cacheable if it ever matters.

---

## 4. Client-generated UUIDs, accepted by the server as primary key

No `remoteId`.

**Why.** Entities are created offline, so identity has to be creatable offline.
One identity for the whole lifetime, and a duplicate create collides on the
primary key — idempotency for free at the record level.

**Cost.** Requires a server that accepts client-supplied ids. Against a legacy
backend that mints its own, this would need `remoteId` and a period where the
entity exists locally with no remote identity.

---

## 5. Idempotency key is the operation's own id

One column. Not a separate field, because with one request per operation the
values would always be identical, and an unused column contradicts the project's
own rule about not building ahead.

**Why keyed on the operation, not the entity.** One entity produces several
operations over time. Keying by entity would make the server treat a later,
different operation as a duplicate and silently discard it.

**Cost.** Local identity and network contract are coupled. If ids were ever
regenerated by a migration, the server would stop recognising work it had already
done. They separate the day one operation becomes several requests.

---

## 6. Payload stored as a JSON blob

**Why.** Operation types need different data. Dedicated columns would be mostly
null and every new type would mean a Core Data migration.

**Cost.** Nothing inside the payload is queryable. Fine, because the engine only
queries `state` and `nextAttemptAt`. Promote a field to a column if that changes.

---

## 7. Core Data, not SwiftData

**Why.** The whole project is about durability and crash recovery, which needs
transparent transactional control. Core Data gives it. SwiftData's write
semantics are less explicit and it is younger in concurrency and migration
behaviour. Core Data is also more likely to match an existing production codebase.

**Cost.** More boilerplate, and a heavier API to test around.

---

## 8. Domain models separate from managed objects

**Why.** `NSManagedObject` is not `Sendable` and is context-bound; letting it
cross actor boundaries is a known crash source. Domain rules stay testable
without a store.

**Cost.** Mapping code in both directions.

---

## 9. Uploads always from file

`uploadTask(with:fromFile:)`, never `Data`, from the very first upload.

**Why.** Background `URLSession` does not accept `Data` at all, and a 400 MB
video in memory gets the app killed by the system. Starting with `Data` means
rewriting everything that touches upload later.

**Cost.** Small files go through a file handoff that they would not strictly
need.

---

## 10. Store file names, not paths

**Why.** The app container UUID changes between installs, updates and restores. A
persisted absolute path becomes a broken reference — in this domain, lost field
evidence.

**Cost.** The directory has to be resolved at every access.

---

## 11. Failure injection from Block 1

The fake backend can delay, time out, return 400 and 500, and commit a write then
fail the response. It deduplicates by idempotency key. The app has a network
toggle.

**Why.** If failure testing is the last phase, everything before it is built on
unverified assumptions. Here the failures *are* the product.

**Cost.** The fake backend is a real piece of work, not a stub.

---

## 12. Whole-file upload before chunking

**Why.** Feel the problem first. `uploadTask` has no resume, so a dropped
connection at 80% restarts from zero. Experiencing that is what makes the chunked
design a decision rather than a recital.

**Cost.** Known rework, accepted on purpose.

---

## 13. No conflict resolution between device and server

Single-writer, push-only. This says nothing about concurrency inside the app,
which is real and is dealt with in 18.

**Why.** One inspector owns one assessment on one device. Conflict handling would
add machinery with no scenario to justify it.

**Cost.** This closes the door on server-side edits to in-progress assessments,
and on any back office assigning work to inspectors. Assessments originate on the
device, full stop. Reopening that would mean deciding what happens when the
server changes a record the inspector has already edited offline.

---

## 14. Fake backend in Python

FastAPI over SQLite.

**Why.** The backend is a test instrument, so the language is free — and Python
is worth learning alongside. FastAPI handles multipart upload, async, and
request validation with very little code, which keeps the backend from competing
for attention with the iOS work.

**Cost.** A second language and toolchain in the project. Contained, because the
server stays small on purpose.

---

## 15. The evidence file is filed before its record is written

A capture produces two writes: the media file into the evidence directory, and
the row that points at it. No transaction spans the filesystem and Core Data, so
one of them lands first. The file does.

**Why.** One of the two crash windows has to exist, and they are not equally
bad. File first leaves an orphan file — garbage, identifiable, deletable. Record
first leaves a row pointing at a file that does not exist, which in this domain
is field evidence the inspector believes was captured and cannot be recovered.
The asymmetry decides it.

The file is named after the evidence id, so an orphan identifies itself: the
sweep is "is there a row with this UUID?", with no auxiliary index and no
scanning of stored file names.

**Cost.** R8 says walking away leaves nothing behind, and an interrupted capture
does leave the orphan file. Holding R8 literally needs a sweep at launch that
deletes files in the evidence directory with no matching row. Not built yet, and
tracked as known debt rather than discovered later.

---

## 16. Creation and the first input are one write

An assessment is not created empty and then filled. `CreateAssessment` takes the
first input — text or a capture — and writes the record with it, in one call.

**Why.** The alternative is create-then-add, which is two transactions with a
gap. The app dying in that gap leaves exactly the empty assessment R8 forbids.
In a project whose subject is termination mid-operation, introducing a two-step
create would be building the bug on purpose.

**Cost.** Two `execute` overloads instead of one, and Presentation carries an
`assessmentId: UUID?` to know whether the next input creates or updates. That
branch is real — a fresh screen and an existing draft are genuinely different —
so naming it beats hiding it behind an upsert.

---

## 17. Draft writes are debounced, and flushed on blur and on background

Typing does not write per keystroke. Writes are debounced, and forced
immediately when a field loses focus and when the app leaves the foreground.

**Why.** R7 originally promised "no state that exists only in memory", which is
not implementable — a debounce window *is* memory-only state, and even writing
on every keystroke leaves the gap between the key event and the commit. Since
the window cannot be removed, the useful question is where to put its edges.
Blur and backgrounding are where a person expects their input to be safe, and
backgrounding is also the last moment the app is told about before the system
can kill it.

Per-keystroke writing was the alternative. It buys a window shorter than a
person can perceive, at the price of a Core Data transaction per character on a
device that may be recording video at the same time.

**Cost.** An abrupt kill during continuous typing loses the last debounce
window. That is real, and it is accepted: the inspector loses a fraction of a
sentence they were still writing, never a field they had finished. R7 was
rewritten to promise that instead of promising zero.

The domain side is already shaped for this — `Assessment.applying(_:at:)` takes
a batch of edits, so a flush writes every touched field in one transaction
rather than one per field.

---

## 18. Writes are compare-and-set, not last-writer-wins

Every use case reads an assessment, computes a new one, and writes the whole
aggregate back. `update` now refuses the write unless the stored version is
still the one that was read.

**Why.** The read-modify-write shape is lossy without it, and the windows are
not theoretical. `AddEvidence` holds one open across filing the media;
`UpdateAssessment` holds a shorter one. R7's debounced autosave fires on a
timer, so a note flushed while a video is being filed was being reverted by the
snapshot taken before it. Worse, `adding` copies `status` from that snapshot,
so a completion landing in the window would have been rolled back to `open` —
taking R6 with it, and leaving a draft carrying sync operations, which R10 says
cannot exist.

The version travels inside the value: an edit returns `version + 1`, so a write
states which predecessor it expects without a separate parameter to forget.
`updatedAt` was considered as the token and rejected — tests inject a fixed
clock, so two legitimate writes would share a timestamp and the check would
pass exactly where it needs to fail.

Retrying re-runs the transform against freshly read state, which is what stops
the guards inside it from judging a stale snapshot. Retries are cheap because
everything expensive happens first: the media is already filed and the evidence
id already minted, so a second attempt moves no files and creates no orphans.

**The alternative.** Narrow the port so it takes the change rather than the
aggregate — `apply(_ edits:to:)`, `append(_ evidence:to:)`. That removes the
loss by construction and appends never collide. Rejected because the R6 guard
would then have to run inside the repository to see fresh state, putting a
domain rule in the Data layer.

**Cost.** A `version` column, a retry loop, and a conflict that callers can
receive. Three attempts is a guess: with one logical writer collisions are
rare, and a single retry would almost always do.

---

## Designed but not built: chunked upload

Recorded because the design is the deliverable, whether or not the code follows.

Protocol: `POST /uploads` returns an `uploadId`; `PUT /uploads/{id}/parts/{n}`
per chunk; `POST /uploads/{id}/complete` assembles.

Client: read a window with `FileHandle`, write it to a small temp file, upload
that temp file, delete it, advance. Never slice into `Data`.

The Operation stays a single row and carries `uploadId`, `chunkSize`,
`totalChunks`, `nextChunkIndex`. Not 80 rows — that pollutes the queue and makes
ordering harder. The idempotency key moves down a level, to
`uploadId + chunkIndex`.

**The interesting tension.** Background sessions exist to run while the app is
suspended, but chunking needs someone to decide to send the next chunk after each
response. A suspended app cannot decide anything. The system grants a brief
wake-up via `handleEventsForBackgroundURLSession`, but will not do it eighty
times generously. Mitigations: enqueue several chunks at once rather than one at
a time, use larger chunks to reduce round trips, and accept that progress
advances in bursts and resumes when the user opens the app.
